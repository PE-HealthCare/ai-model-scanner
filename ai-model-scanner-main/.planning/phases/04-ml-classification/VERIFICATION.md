# Phase 04 — ML Classification — VERIFICATION

**Source of truth:** `AI_Model_Scanner_FINAL_MASTER_DISCOVERY_GRAPH.md`
**Gate:** CP4 — ML Gate (Master Graph §13)
**Applies to:** `PLAN.md` in this same directory.

This phase does not pass CP4 until every gate below is satisfied. Any DECISION
REQUIRED item referenced here remains open; verification of this phase does not
imply those decisions have been made.

## G1 — Temporal Dependency Respected

- [ ] Confirmed: Phase 03 (P1 Static Steganalysis) has passed CP3 — Static Gate
      before any output of this phase is treated as final/authoritative.
- [ ] No final classifier training run is dated/logged prior to P1 Phase 3
      verification completion.
- [ ] Preparatory work (corpus assembly, synthetic tampering design, LightGBM/
      TreeSHAP scaffolding) is clearly distinguishable in artifacts/logs from
      final training work.

**Fail condition:** a "final" `lightgbm_model.txt` exists or is referenced as
authoritative without a corresponding verified P1 Phase 3 (CP3) completion.

## G2 — Training-Data Consistency

- [ ] Training feature dataset (clean + synthetic tampered corpus) was produced
      using the **same** extraction code/semantics as P1's inference-time
      `features.json` output — not a separate or reimplemented extractor.
- [ ] Synthetic tampering generation methodology is documented and its outputs
      were passed through the identical P1 extraction path used at inference.
- [ ] No divergent preprocessing, normalization, or feature engineering step
      exists between training-time and inference-time extraction.

**Fail condition:** training features are generated by any code path other than
P1's verified extractor, or any transformation is applied at training time that
is absent at inference time (or vice versa).

## G3 — Feature Semantic Consistency

- [ ] Feature names used in training match feature names in inference-time
      `features.json` output, exactly.
- [ ] Feature order in the training matrix matches the order used at inference.
- [ ] Feature meaning/semantics are unchanged between training and inference
      (i.e., no silent redefinition of what a named feature represents).
- [ ] No fixed/invented feature-vector dimensionality (e.g., an assumed "18-D"
      vector) is hardcoded independent of the actual P1-verified feature schema.

**Fail condition:** any mismatch in name, order, or meaning between training-time
and inference-time features; or a hardcoded dimensionality not traceable to the
agreed schema (D1).

## G4 — Classifier Artifact Validity

- [ ] `lightgbm_model.txt` is produced only from a training run that used
      P1-verified real features (not mock/placeholder features).
- [ ] The artifact is traceable to the specific feature semantics/version it was
      trained against (even if the exact staleness-check mechanism, D8, is not
      yet finalized — traceability documentation is still required).
- [ ] Model file loads successfully and produces predictions on real
      inference-time feature input without shape/type errors.

**Fail condition:** the shipped `lightgbm_model.txt` was trained on mock/
placeholder features, or cannot be traced to a specific feature-semantics
version, or fails to load/predict on real P1 output.

## G5 — Inference Compatibility

- [ ] The trained classifier accepts real `features.json` output from P1 Phase 3
      without requiring any undocumented transformation.
- [ ] `ml_results.json` is produced end-to-end from real P1 features through the
      trained classifier (not from mocked ML results).
- [ ] P_tamper values are within the expected [0,1] range (or documented range)
      for a representative set of real test inputs.

**Fail condition:** inference on real P1 features throws, requires undocumented
glue code, or produces out-of-range/undefined P_tamper values.

## G6 — TreeSHAP Validity

- [ ] TreeSHAP attribution is computed against the final trained model (not a
      scaffold/mock model).
- [ ] SHAP values are attributed to the exact same feature names/order used in
      training (no silent remapping).
- [ ] SHAP output is verified to sum/relate to the model output consistent with
      standard TreeSHAP guarantees (e.g., additivity property spot-checked).

**Fail condition:** SHAP attribution references feature names/order inconsistent
with the trained model's actual feature schema, or is computed against a
non-final/mock model and presented as verified.

## G7 — Feature-to-Layer Mapping — Separation Maintained

- [ ] TreeSHAP feature-level attribution output is present and distinct from any
      highest-risk-layer output.
- [ ] No code path derives "highest-risk layer" directly from TreeSHAP values
      without an explicit, separate feature↔layer aggregation step.
- [ ] If a feature-to-layer aggregation mechanism is implemented in this phase,
      it is clearly flagged as addressing **D6 (DECISION REQUIRED)** and is not
      presented as though it were part of the originally frozen architecture.
      (If not implemented, this box is satisfied by confirming no such conflation
      exists.)

**Fail condition:** highest-risk-layer is computed as a direct reinterpretation
of SHAP values without a documented, separate aggregation mechanism; or D6 is
silently treated as resolved without being flagged.

## G8 — Retraining Requirement Enforcement

- [ ] A documented process (manual or automated) exists to detect when P1
      feature semantics change (name, meaning, representation, or order).
- [ ] Documentation explicitly states that any such change requires: P3 retrain
      + TreeSHAP remap/reverify + Phase 4 re-verification (per Master Graph §7,
      §14).
- [ ] It is acknowledged in documentation that LightGBM may continue to run
      without error on stale/mismatched features (the "fails silently" risk from
      Master Graph §7), and that successful execution alone is not evidence of
      validity.

**Fail condition:** no documented retraining trigger/process exists, or
documentation asserts that "the model still runs" is sufficient evidence that
retraining is unnecessary.

## G9 — Non-Invention Check

- [ ] Implementation does not resolve D1 (ml_results schema fields) unilaterally.
- [ ] Implementation does not resolve D6 (feature-to-layer aggregation) as if it
      were a finalized part of the frozen architecture.
- [ ] Implementation does not resolve D8 (staleness protection mechanism) and
      present it as mandatory/finalized without team sign-off.
- [ ] No architecture redesign relative to Master Graph §1, §7, §18 has occurred.

**Fail condition:** any DECISION REQUIRED item from the Master Graph is treated
as resolved without explicit team sign-off recorded elsewhere.

## Gate Outcome

CP4 passes only when **all** boxes in G1–G9 are checked, and only after CP3
(Phase 03 Static Gate) has independently passed. Partial completion does not
authorize advancing to Phase 05 per Master Graph §19 ("Advance only after
VERIFICATION.md passes").
